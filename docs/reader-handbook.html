用户增长6步法

把增长问题说给智能体听，一步步找到先改什么、怎么做、怎样判断有没有用。

注册的人多，但真正使用的人少？用户不回来，或不知道先改产品、转化还是获客？这个 Skill 会复用你已有的信息，每轮先问一个关键问题，最后整理成可以交给团队讨论的 HTML 增长行动报告。你不需要先懂增长术语，也不需要会写代码。

这是面向不同智能体的 Agent Skills 技能包，不是独立软件，也不限于 Codex。支持 Skills 的应用可以安装；能读取工作区文件的智能体可以临时加载。仅能聊天、不能读完整资料或生成文件的应用，能力另有限制，见安装指南。

第一次使用，只做四件事：安装或加载 → 说出问题 → 回答追问 → 打开报告。

安装或加载

不熟悉命令：先把这段话发给你的智能体

适用于能够联网并管理本地或云端工作区的智能体。在你平时使用的应用里，直接复制：

请帮我安装「用户增长6步法」：
https://github.com/sushengs-creator/user-growth-six-steps/tree/main/skills/user-growth-six-steps

先检查当前应用支持的 Skill 安装方式，再安装完整技能包。完成后请实际读取 SKILL.md 和相关参考文件，确认当前对话可以使用，并说明能否生成可下载的 HTML 报告。如果本应用不支持安装，请明确告诉我，给出这里可用的加载方法。

如果应用只能回答文字、无法下载或安装文件，就用下面的手动方法。收到“已记住”不等于装好了；要确认它实际读到了技能文件。

会用终端：一条命令，按提示选择自己的应用

在你希望使用 Skill 的工作文件夹内，打开终端并运行：

npx skills add sushengs-creator/user-growth-six-steps --skill user-growth-six-steps

需要已安装 Node.js 和 npm/npx。工具会显示检测到的智能体；确认是你使用的应用，按提示选择安装范围。选 Project 只在当前项目使用，选 Global 用于该应用的个人范围。不要照抄选择别人的应用，也不必给所有应用安装。命令来自 Skills CLI，支持范围以它当前显示的列表为准。

无法自动安装：下载后交给应用加载

直接下载已打包的 Skill ZIP。应用有“上传 Skill”入口时，上传这个 ZIP；需要放入本地 Skills 目录时，解压后复制整个 user-growth-six-steps 文件夹。不需要自己重新打包，也不要只复制 SKILL.md，它还要读取配套参考文件。

不知道放在哪里？跨平台安装指南列出了已核验的目录、导入注意事项，以及不支持原生 Skills 时的工作区加载办法。本机安装不会自动同步到云端智能体，云端也需要能读到完整技能包。

安装后，确认当前对话已经能用

在新对话中发送：

请检查你是否能使用「用户增长6步法」（user-growth-six-steps）。实际读取技能说明，告诉我读到的文件位置，并确认能否提供 HTML 文件或下载附件。先不要开始业务诊断；如果没有找到文件，请如实说明。

成功的标志是：它能指出实际加载的 SKILL.md，并说明报告交付能力。如果找不到，先按安装指南排查；仅复述本页介绍不能证明已加载。

请使用「用户增长6步法」（user-growth-six-steps）。

还没整理数据，也可以只说：

请使用「用户增长6步法」（user-growth-six-steps）。我们做面向小商户的排班工具，很多人注册后没有发布第一张排班表，暂时没有完整数据。请先带我判断需要了解什么，每轮只问一个问题。

上面是虚构业务示例，换成你的业务即可。先用自然语言点名技能；$ 不是所有应用通用的语法。 Codex 可用 $user-growth-six-steps；Claude Code 可用 /user-growth-six-steps；其他应用按它自己的技能选择方式调用。加载与调用是两步，单发名称不会自动完成安装。

接下来，回答它当轮的问题即可。有报表、反馈或现成方案就直接附上；它应先用这些材料，再问真正影响判断的缺口，不必让你从头重说。

资料暂时补不上、想先拿到能讨论的版本时，直接回复：

我暂时没有更多数据。请先基于已有材料生成 HTML 草案和 JSON，标清事实、假设和待补资料，给出下一步最小行动。

不需要坚持聊满六步，也不保证固定三轮就能解决所有问题。材料充分时可以直接出报告；材料有限时先交草案。

操作示范

以“新店注册后不完成首次盘点”为例，看怎样从提问走到行动草案。

下面是一段虚构对话示范，与仓库现有报告采用同一组材料；它展示使用方式，不是实际运行记录或真实增长成果。你可以照着表达，把产品、数字和约束换成自己的。

1. 复制口令，说出当前问题

请使用「用户增长6步法」（user-growth-six-steps）。我们做小店库存管理工具，想改善新店注册后不完成首次盘点的问题。这一批有80家新注册店铺，每家都观察满7天，24家完成盘点。请每轮先问一个关键问题，最后交付HTML行动草案和JSON。

2. 逐轮补充信息，不必先写完整需求书

第一轮：把“完成”说清楚。

AI：你们怎样判定一家店完成了首次有效盘点？

你：需要导入真实货品、录入实际库存，并确认盘点结果。按店铺去重，每家只计首次完成；24家都符合这个定义。

第二轮：找优先调查的线索。

AI：未完成盘点的店主，具体在哪一步遇到了困难？

你：我们问过5位未完成者，其中3位说导入字段说明不清楚。还没有完整的导入、纠错、确认环节数据。

第三轮：把建议接到实际分工。

AI：这轮排查与改进的人员安排确定了吗？

你：还没确定，开发工作量和实际排期也待确认。请先建议产品、开发和运营各自做什么，基于已有信息生成草案，缺少的数据列成待补项。

这时即可交付本轮报告，不必为了凑齐六步继续盘问。负责人和排期会标明是建议安排，留待团队确认。

3. 看懂报告：当前能判断什么

报告会把 24÷80＝30% 记为“7天首次有效盘点率”的虚构基线。这是本轮局部激活指标，业务北极星仍待确认。3位反馈者提供了调查线索，还不足以证明字段说明是主要流失原因。

六步状态会如实保留：北极星、增长模式待核对；核心杠杆正在调查；魔法数字因缺少行为与后续使用记录而暂受阻；策略尚待任务观察支持；验证尚未运行。

报告的行动节选如下：

先做什么建议分工，待确认怎样决定下一步
观察导入、纠错、确认的任务过程，复核事件记录产品负责人区分字段不懂、资料未准备和操作故障；若主要障碍不同，调整方向
观察支持后，评估字段例子与导入预览产品与开发工作量确认后再排期；出现错导或错误确认时暂停并排查
回收口径可比的后续结果运营或数据负责人每店观察满7天后复盘；继续门槛需在上线前确定

先安排排查和方案准备，取得实际结果后再判断是否增长。 未取得随机对照数据时，前后变化只写成观察结果，不写成AB实验已验证有效。

查看这组材料对应的现成产物：HTML报告（下载后用浏览器打开）和可编辑JSON。报告包含当前判断、六步状态、事实与假设、缺口、指标、行动、验证安排及来源限制；这些文件也明确标注“公开演示、草案”。

4. 做完后，带着结果继续

把原JSON和真实观察记录附给你使用的智能体，再复制：

请使用「用户增长6步法」（user-growth-six-steps），继续这份增长草案。请读取我附上的原JSON和本轮观察记录，区分已确认事实与仍待验证的假设，判断应继续、修改还是停止原方案。不要补造未知数据；更新HTML和JSON，并说明这次改变了哪些判断。

如果只想核对某个结果，可以加一句“本次只回答这个问题，不需要HTML”。

六步方法论

六步主线来自卢壮华《增长杠杆：探索用户增长的6步法》。本 Skill 把这条判断链组织为对话和可执行报告；以下是每步要解决的实际问题。

步骤核心问题形成的产物
1. 确定用户增长的北极星指标什么增长代表用户与业务真正获得价值？有行为、对象、周期和计数口径的指标卡
2. 认清合适的用户增长驱动模式用户为什么来、留下、付费或带来其他人？当前主导与辅助动力，以及支持证据
3. 确认用户增长的核心杠杆在现有资源内，先改哪一处最值得？少数优先机会及选择理由
4. 寻找用户增长的魔法数字哪个行为阈值可能关联后续价值？有数据支持的候选，或寻找阈值的采集计划
5. 基于魔法数字设计用户增长策略怎样帮助目标用户完成有价值的行为？人群、改动、资源、负责人和验证指标
6. 通过AB实验验证用户增长策略效果结果支持什么判断，是否继续投入？验证设计，以及取得真实结果后的阶段决定

这六步有几个关键连接：先确定目标，才知道应该优化什么；先找到杠杆，才有理由选择策略；行为与结果相关，只能产生候选假设，不能证明强制用户做到某个次数就有效；最后用与业务条件相称的验证支持决定。

没有找到魔法数字时，也可以针对有证据的体验问题做探索。 有限资源可以先安排低成本试用或观察；如果没有随机分组，就如实称为前后观察。局部激活率也不自动等于整体北极星。

详细的输入、判断、输出、常见误用和贯穿案例见 用户增长6步法方法论。

这个 Skill 的价值

  • 减少无效讨论。 每个问题都服务于下一项判断，已有信息直接复用。
  • 把建议连接到证据。 区分用户事实、作者方法、历史案例和本次假设，数字与结论能追溯。
  • 让行动可执行。 明确先改变什么、由谁做、受什么资源限制，以及如何判断是否继续。
  • 保留不确定性。 缺数据时给出补证任务，不为完整表格编造阈值、样本或增长幅度。
  • 留下可复用的产物。 HTML供团队阅读，JSON支持后续更新，减少下一次诊断重新开始的成本。

适合已有产品或服务的活跃、留存、转化与增长验证问题。若产品价值或商业模式尚不清楚，会先澄清这些前提；本资料不提供完整的广告平台操作教程。

安装与第一次使用

用户增长6步法是一套交给智能体使用的工作流程。安装后，你描述增长问题，智能体按需要追问，再把判断、行动和验证计划整理成报告。你不需要先学会六步法，也不需要会编程。

它采用 Agent Skills 开放格式，并非某个智能体产品专用。格式通用不等于每个聊天工具都有安装入口：请按下面与你环境相符的方式使用。

适用于具备联网、文件操作和 Skill 安装能力的智能体。复制下面整段发送给它；这是安装请求，还没有开始分析你的业务。

最少准备什么

先说明这三件事就能开始：

  1. 你做什么，服务谁。 例如产品、服务或具体功能及其用户。
  2. 你遇到什么问题。 比如注册多但使用少、留存下降、转化停滞，或不确定一次实验该不该推广。

对话会怎样推进

Skill 先提取已有的事实、目标与约束，再判断本次是完整诊断还是局部问题。需要完整诊断时，沿着原书六步推进：

步骤你会得到什么
确定用户增长的北极星指标核心价值与指标口径
认清合适的用户增长驱动模式当前主要增长动力及依据
确认用户增长的核心杠杆值得优先投入的少数机会
寻找用户增长的魔法数字行为阈值候选，或寻找它的数据计划

通过AB实验验证用户增长策略效果与业务条件相称的验证和决策规则

它每轮只追问当前必要的1—3个短问题，优先问一个。你回答后，它会说明新增判断，再继续推进。未知数据不会被填成0，尚未验证的假设不会写成事实。

这不是必须完成的长问卷。你可以从已知问题进入某一步，也可以要求先交付草案。

四种常用口令

1. 继续已有诊断

在同一段对话中直接补充信息：

继续使用「用户增长6步法」（user-growth-six-steps）。沿用前面已经确认的指标和业务背景。新增材料如下：[数据或反馈]。请更新受影响的判断，告诉我下一步先做什么。

换到新对话时，附上上次的报告、JSON 或必要背景：

使用「用户增长6步法」（user-growth-six-steps），继续这份报告。附件是上次的 HTML 和 JSON，新增事实是：[变化]。请先读取已有结论，只复核被新事实影响的部分。

Skill 不保证自动记住另一段对话。把已有产物带到新对话，可以减少重复说明。

2. 只处理一个局部问题

使用「用户增长6步法」（user-growth-six-steps）。这次只检查[指标口径/转化瓶颈/魔法数字/实验结果]。已有材料如下：[材料]。请直接处理本次问题，只补问会改变结论的前提，先用文字回答，不需要 HTML。

例如检查实验时，提供实际分组方式、每组人数、成功人数、观察窗口、事前目标和其他已知变化。Skill 会区分观察差异、统计证据和业务目标，不要求从业务介绍重新开始。

3. 数据不全，先拿到方案

你会先得到可用的阶段产物。后续补齐数据，再更新同一份报告。

4. 复盘已经执行的行动

使用「用户增长6步法」（user-growth-six-steps）。我们执行了报告中的[行动]，实际情况如下：[人群、时间、实施范围、结果与同期变化]。请判断哪些假设得到支持、哪些仍不能确认，更新继续、修改或停止的建议，并生成新版 HTML 与 JSON。

如果实际只有前后观察，直接说明即可。Skill 不会因为六步名称包含 AB，就把你的观察改写成随机实验。

最终会交付什么产品

当你需要完整方案或阶段报告时，主要产物是两份实际文件：

文件用途
单文件 HTML 增长诊断与行动验证报告用浏览器阅读、分享给团队、打印或在打印功能中保存为 PDF
可编辑 JSON保存报告的结构化内容，便于补充数据后继续生成新版报告

HTML 包含内嵌样式，不依赖网络字体、CDN 或外部脚本。优先由智能体运行配套 Python 3 脚本生成；没有 Python 但能创建文件时，可按相同规范直接生成，并说明未经过配套脚本校验。只能输出文字时，应明确提供的是供手动保存的源码，不能声称已生成文件。JSON 面向后续更新，你无须手动学习或填写它。

本地应用应提供实际文件链接，云端应提供下载附件或可访问的文件链接。下载 HTML 后用浏览器打开，先看当前判断，再看优先行动与待补资料。保存 HTML 和 JSON，换会话时一并提供。GitHub 上的公开 HTML 示例需要点击 Download raw file 下载，才能作为网页打开。

如果应用只说“已生成”却没有文件，回复“请提供实际 HTML 与 JSON 文件或可下载附件；如不能创建文件，请说明具体限制”。

报告会清楚呈现：

  • 当前最重要的增长判断，以及它的证据强度。
  • 六步分别进行到哪里；未涉及、待补资料的步骤保持真实状态。
  • 已知事实、待验证假设和影响决策的信息缺口。
  • 指标定义、对象、周期、分子分母与已知数值。
  • 优先行动、负责人、范围、时间，以及继续或停止的依据。
  • 验证方法、还需取得的数据、来源及结论限制。

仅有方案时，第6步不会显示实验已经完成。报告标记“定稿”，只表示本次文稿已经完成，不表示增长已经实现。

简短的指标或实验核查可以只交付文字；明确要求其他形式时，也不强制生成 HTML。

怎样得到更有用的结果

把“帮我提高增长”改成一个带对象和现象的问题，例如“新注册商户建完表但没有发布，先改哪一步”。如果已经决定本周只改善发布入口，就直接说明，Skill 会在这个范围内工作。

把证据与解释分开提供，例如“20家成功发布”是记录，“他们可能看不懂入口”是待验证解释。对于同一指标，尽量说明统计对象和时间，避免把用户数、次数、商户数混在一起。

如果不确定一个数字是否来自真实数据，直接标注“不确定”。Skill 可以帮助核查依据；它不能把作者案例、演示数据或其他产品的阈值变成你的经营事实。

这份 Skill 帮你形成有依据的判断、可执行的行动和可复核的验证计划。产品改动、实验运行和经营收益需要在真实业务中实现；它交付的报告是推动这些工作的工具。

用户增长6步法：从增长问题走到可验证的行动

增长讨论常从“做什么活动”开始。用户增长6步法先把问题往前推一层：我们希望哪一类用户，持续获得什么价值；当前最值得改变的环节是什么；怎样知道这次改变有效？

这份 Skill 将卢壮华《增长杠杆：探索用户增长的6步法》的六步判断流程，整理为可以在对话中使用的方法。它会读取你的业务材料，围绕关键缺口少量提问，把事实、假设和待补信息分开，最终形成可以执行和复盘的 HTML 报告。

六步连接的是一条判断链：

确定目标 → 解释增长动力 → 找到优先杠杆 → 提出行为阈值候选 → 设计改变 → 验证效果。

六步名称来自原书；对话引导、报告结构、状态管理和下面的演示，是本 Skill 的应用设计。

当前为预发布版本。 图书第1—7章正文、附录和后记已读完，部分图片待核；两个指定微信专辑合并为10篇独立文章，已读6篇，4篇待补。方法只采用实际读取的内容，不声称已完成全部图文整合。

谁适合使用

已经有产品或服务、能够说明目标用户和业务目标，却不知道该先改善哪里的人，可以用它梳理活跃、留存、转化、获客与策略验证问题。产品经理、运营人员、创业者和增长团队都可以从自己的职责范围进入。

如果你只有一个产品设想，尚未确认真实需求或商业模式，Skill 会先指出这些前提缺口，帮助你安排补证。它不能靠填满六步表格证明市场需求成立。

如果你已经明确北极星指标，只想审查一次实验，便可以直接进入第6步。六步是判断框架，每次对话不必从第一步重新问起。

一个贯穿六步的例子

下面是一款完全虚构的小商户排班 SaaS，只演示如何应用方法。产品、数据、访谈和策略均为本文编写，不是原书案例，也不是已经验证的经营结果。

商户用它安排员工一周的班次。团队的问题是：“不少人注册了，但没有真正开始排班。我们只有两天开发资源，先改哪里？”

已有演示材料：在具备完整7天观察窗口的200家新注册商户中，100家开始建表，80家建完，20家成功发布。12位未发布者的演示访谈中，9位提到不知道发布入口在哪里。

这批材料足以支持一个值得检查的发布问题，尚不足以证明它是整个业务的唯一增长瓶颈。六步会把这两个判断分开。

第1步：确定用户增长的北极星指标

解决什么： 团队究竟希望增长什么，为什么这个指标能够代表用户和业务获得价值。

需要的输入： 核心用户、核心任务、业务阶段、企业目标，以及用户自然使用产品的频率。

怎样判断： 指标应表达有价值的行为，并写清行为定义、计数对象、周期和去重方式。累计注册人数不能直接代表有效使用；也没有适用于所有产品的 DAU、MAU 或付费人数答案。

本步输出： 一张指标卡：名称、价值解释、事件定义、对象、周期、计数口径，以及仍未确认的部分。

在排班例子中，可以讨论“每周成功发布有效排班表的商户数”是否适合作为北极星候选。演示中的“有效”暂定义为至少涉及2名成员、覆盖完整工作周并成功发布，后续仍须确认它是否代表商户真正完成了任务。

本周要改善的“注册后7天内首次有效发布率”是局部激活指标。它可以服务于北极星，但局部指标定义清楚，不代表整个业务的北极星已经得到确认。

容易误用： 为了方便统计选择一个没有价值含义的数字；把案例中的指标直接搬到自己的产品；把某次活动指标升格为长期业务目标。

第2步：认清合适的用户增长驱动模式

解决什么： 用户为什么会来、留下、付费或带来其他用户，当前增长主要依靠什么机制。

需要的输入： 用户获取价值的过程、实际获客方式、购买过程、内容或服务供给，以及目前的团队资源。

原书讨论四类驱动模式：

模式需要理解的机制
产品驱动 PLG产品的核心功能和体验如何解决用户问题
销售驱动 SLG销售、分销及服务如何推动客户选择和使用
营销驱动 MLG品牌与营销如何传达价值、形成认知和选择
运营驱动 OLG内容、货品、服务的供给与分发如何创造价值

怎样判断： 用实际路径解释机制，再讨论主次。模式可以混合，也可能随阶段改变；一个标签不能代替对业务的理解。

本步输出： 当前主导动力、辅助动力及其证据，以及这对资源投入的含义。

排班 SaaS 可以提出一个假设：用户能否快速完成真实排班任务，是当前产品驱动的重要部分。但只有当使用记录和反馈支持这一判断时，才值得进一步围绕产品体验集中资源。不能仅因为它是 SaaS，就认定销售或服务不重要。

容易误用： 看产品类型就贴标签；在尚未理解动力前，把签到、补贴、投放或裂变当成默认答案。

第3步：确认用户增长的核心杠杆

解决什么： 影响增长的因素很多，有限资源现在应该投向哪一处。

需要的输入： 指标分解、关键角色、主要路径，以及按人群、来源、场景或使用状态拆分的数据与反馈。

怎样判断： 先确保数据可比，再比较机会空间、用户价值、证据强度和实施难度。业务公式必须满足同一范围、时间和分母关系；使用者、发起者、管理者、影响者、购买决策者可能是同一个人，不能重复计数。

本步输出： 少数优先杠杆，每个都说明证据、可能机制和排序理由。

在演示的同一批200家商户中，总体首次发布率为20÷200＝10%；已建完商户的发布率为20÷80＝25%。二者分母不同，回答的问题也不同。

建完后未发布的人数与访谈提示，让“发布入口不清楚”成为值得优先验证的局部杠杆。两天开发限制进一步影响排序。这里的决定是“先检查并改善这处摩擦”，并非“已经证明它造成全部流失”。

容易误用： 只挑最低转化率就认定主因；用不同窗口或人群的数据直接比较；为了算公式而强行相乘；用没有依据的评分包装主观判断。

第4步：寻找用户增长的魔法数字

解决什么： 哪个具体、可操作的用户行为，可能帮助用户持续获得价值；行为达到什么程度时，结果出现值得关注的变化。

需要的输入： 用户调研、明确的行为定义、完整观察窗口，以及行为与后续结果的关系数据。

怎样判断： 先提候选，再检查行为量与结果的关系及变化位置。检查行为是否发生在结果之前，避免把结果发生后的行为当成原因。相关关系只支持进一步验证，不能直接证明强制用户做到某个次数就能带来增长。

本步输出： 一个有依据的行为阈值候选，或一份寻找阈值所需的数据计划。没有数据时，数字保持待求。

排班团队可以提出一个待研究的问题：“注册后的前两周，是否在两个不同周都成功发布过有效排班的商户，更可能在第4周继续使用？”这只是一个采集和比较方向，两次并非已经找到的魔法数字。需要先确认记录、时间先后、完整窗口和可能的其他差异。

如果当前只有首次发布的数据，Skill 会保留这一缺口。发布入口存在明确体验问题时，团队仍可以先做探索性改善，不必先编一个阈值才能继续。

容易误用： 套用其他产品的好友数、使用次数或报告次数；把“成功用户常做什么”写成“让所有人做什么必然成功”；把次数越多越好当成普遍规律。

第5步：基于魔法数字设计用户增长策略

解决什么： 如何改变真实体验，让目标用户更容易完成有价值的行为。

需要的输入： 目标人群、核心杠杆、候选行为、用户主要操作路径，以及资源和时间限制。

怎样判断： 把策略写成可以检验的假设：为谁改变哪个环节，预计促进什么行为，再检查是否改善目标指标。可以沿着原书的黄金体验路径和体验地图找出不理解、等待、异常或繁琐之处；需要讨论重复使用时，再考虑触发、行动、奖励、投入各环节是否创造真实价值。

本步输出： 可执行的行动卡，包括改动、范围、负责人、时间、验证指标，以及继续、修改或停止的依据。

排班例子的探索策略可以是：在建表完成页明确显示发布入口，并解释发布后员工能看到什么。行动的假设是“入口与结果更清楚，能够减少商户建完却未发布的情况”。开发范围限定在本周两天资源内。

这项策略尚未证明有效，魔法数字也仍未确定。报告会如实保留状态，不把一个产品建议写成已验证的增长结论。

容易误用： 输出一长串活动清单，却说不清各自对应哪种障碍；为了提高次数增加无意义操作；把体验模型当成能自动算出转化率或魔法数字的公式。

第6步：通过AB实验验证用户增长策略效果

解决什么： 观察到的变化能支持什么结论，足不足以决定继续投入或扩大覆盖。

需要的输入： 具体假设、主要指标、实际分组或观察方式、人数与计数、完整时间窗口、同期变化，以及要支持的业务决定。

怎样判断： 根据规模、资源与归因需求选择验证方式。有条件做随机 AB 时，检查分组、分析单位、样本、运行与停止规则。资源较少时可以先做小范围试用或前后观察，但应使用真实的方法名称，并保留归因限制。

本步输出： 验证计划；取得真实结果后，再形成继续、修改或停止的阶段决定。

排班团队若能随机按商户分组、保证两组观察窗口一致，可以比较不同入口下的首次有效发布率，并关注发布失败、错误发布等影响。若只能先给少数商户试用，则先记录是否找到入口、是否成功完成任务，再评估下一步。

当团队只有改版前后两个时段的数据时，报告会写“前后观察”，不会写“随机 AB 已通过”。局部发布率提高，也不能自动证明长期留存或收入已经提高。

容易误用： 只有两个百分比就宣称显著；把前后变化全归因于改动；把统计显著等同于达到业务目标；不断补样直到结果显著；把交付实验计划写成实验已经完成。

使用 Skill 后，决策会发生什么变化

面对“注册后不使用”的问题，你会得到一条能追溯的解释：目前知道什么，哪处最值得先动，依据是什么，哪些数字还不能定，如何实施，以及如何判断是否继续。

Skill 会复用你已经提供的材料，只追问影响当前决定的缺口；每轮通常先问一个关键问题，最多1—3个短问题。已有完整资料时直接推进。只核查一次实验时直接处理实验；暂时拿不到数据时，仍可先交付标明缺口的方案草案。

主要交付物是单文件 HTML 增长诊断与行动验证报告，以及可编辑的 JSON。报告包含当前判断、六步真实状态、指标口径、优先行动、验证计划、来源和限制，可打开阅读、打印和用于团队讨论。简短核查也可以只用文字回答。

它的价值在于让增长建议具备依据、边界和下一步行动。实际增长收益仍取决于业务条件、方案实施与验证结果；一份报告定稿，不等于策略已经成功。
