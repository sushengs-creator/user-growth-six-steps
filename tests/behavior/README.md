# 行为验证：如何复跑与解释

这些业务、数字和角色全部为虚构测试输入，不是真实用户、客户或增长成果。测试材料不随单 Skill 安装包加载。

- `cases.json`：执行共同契约与原始用户消息。执行者只接收当前案例、当前轮次及共同约束，不应读取评分标准或后续消息。
- `rubric.md`：修改前冻结的五维评分、硬失败与验收门槛，仅交给独立评分者。
- `run-conditions.json`：本轮实际执行条件及无法控制的变量。
- `results.json`：揭示条件标签后的逐例得分、失败与结论。
- [证据ZIP](../../dist/behavior-evidence-20261110.zip)：15组真实生成的双文件、逐维独立评分、文件检查与路由记录。仅绝对工作路径作匿名化替换，业务输出保持原样；运行错误记录保留。不是供智能体安装的技能包。

## 重复同样的比较

1. 保留旧版提交 `b27bec67ae2ace7a94f3b778d47c5ddbc8d5a79f`，与本版分别放在独立只读目录。第三组不加载任何Skill或其参考。
2. 使用同一模型、推理与工具配置，并记录实际版本和限制；每个案例新建会话，每组每例各运行一次。所有组只能读各自授权材料、使用本地文件与shell，无联网或额外用户数据。被测Skill是三组间的预设差异。
3. 把 `execution_contract` 中的执行、交付和交互约束与该案例第一轮消息交给执行者。指定独立输出目录，收集实际HTML、JSON及工具结果。G04第一轮结束后才追加第二轮；保留第一轮文件，不提前暴露后续输入。
4. 固定失败处理规则，保留首次错误与修复记录。不得给某一组人工纠错后拿它与其他组的首次输出直接排名。
5. 把条件名替换为随机标签，交给没有参与实现的评分者，用冻结量规评分；同时实际解析JSON、检查文件与HTML/JSON核心内容。记录产物格式可能泄露条件身份的限制。
6. 先看硬失败，再看逐维、逐例和总分。符合基本可用标准不代表优于基线；不足预设改善门槛就如实报告，不能改权重、删难例或用模板完整度加分。

入口路由只把技能描述清单与R01/R02交给选择者，记录选择和理由，不执行后续任务。无Skill条件记N/A。本轮两版本描述相同，均为2/2；这是描述模拟，不是任何产品真实的自动加载结果。

## 本轮结论

旧版40/40、新版40/40、无Skill39/40，均无硬失败。新版相对两组都未达到预设的明确改善门槛。只有4个主案例、每组单次运行；精确后端模型版本等不可见，且知识资料和生成器属于整个包的差异。不能据此承诺真实增长、所有平台兼容或长期效果。
